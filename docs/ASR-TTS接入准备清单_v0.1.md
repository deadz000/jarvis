## 三、架构约束 —— 请确认你们的服务能满足（或明确告诉我做不到）

这些不是我的偏好，是旧项目实测踩出来的（`踩坑指南`）：

| # | 约束 | 为什么 | 影响你们服务的什么 |
|---|---|---|---|
| 1 | **高频音频通道必须独立于慢速决策循环** | 旧项目音频帧走共享 select 被 `biased;` 饿死，麦克风堆积、永久卡"转录中" | 我会用独立 WebSocket/Socket 连接，不与 Master 调用共用通道 |
| 2 | **长连接必须有业务级心跳**，不能用通用 ping/pong | 旧项目 ASR 断线后静默失效，服务端按"音频流空闲"断连 | 你们的服务若按空闲断连，我需要能发**真实格式的静音 PCM** 保活 |
| 3 | **停播必须本地先停（<100ms 预停），不能等后端** | 旧项目等后端确认，打断延迟十几秒 | 播放侧的本地 stop 我会做在前端；你们只需支持中止合成 |
| 4 | **打断 = 停播 ≠ 取消任务** | 旧项目一开口就 cancel，若意图是"排队/继续"就白烧整次调用 | 这条我已实现（Scheduler 与音频解耦），语音接入不改它 |
| 5 | **播放是受控单例资源，需要授权代次（token）** | 旧项目打断后旧音频"复活"串味 | 我已实现模拟版；接真实音频时替换为真实播放器，token 机制保留 |
| 6 | **概率判断要有确定性兜底** | 旧项目把"嗯嗯""啊啊啊"当指令执行 | 我会先做**确定性噪声过滤**（精确词表 → 全同字符 → 去语气词后有效字符数），再交给意图判断 |

## 四、拿到材料后我会做什么

1. **定义 port**（不先绑厂商，落实 SRS §7.8）：
   ```
   AsrPort:  open() / pushAudio(frame) / onPartial / onFinal / close()
   TtsPort:  synthesize(text) → AsyncIterable<{ audio, isLast }> / abort(requestId)
   ```
2. **实现适配器**，并保留一个 **FakeAsr / FakeTts** 用于确定性测试（沿用 FakeWorker 的思路）。
3. **替换模拟音频层**：`audio-manager.ts` 的播放代次语义不变，只把"分片推进"从定时器换成真实音频播放进度。
4. **前端接麦克风与播放**：Web Audio 采集 → 独立 WS 上行；TTS 音频下行 → 本地播放队列（含 <100ms 预停）。
5. **端到端验收点**：
   - 开口 → 预停播延迟 < 100ms（前端本地停，不等后端）
   - ASR partial 能进事件流且**不阻塞** Master 决策（Master 推理期间语音照常接收）
   - 噪声（"嗯""啊啊"）不触发任务执行
   - 停播后旧播放代次不复活（现在已用模拟层验证过这条不变量）
   - ASR 断线能自动重连，重连期间音频不丢（或明确报告丢了多少）

## 五、建议的接入顺序（降低一次性风险）

| 阶段 | 内容 | 为什么先做 |
|---|---|---|
| **6a** | **先只接 TTS** | 面板立刻"会说话"，能直接看到/听到结果播报；且能验证约束 3/5（预停、代次不复活） |
| **6b** | 再接 ASR（先不做 AEC） | 语音输入进来，验证约束 1/2/6 |
| **6c** | 补回声消除与插话判定 | 验证约束 4，处理"播放被自己麦克风拾到"的问题 |
| **6d** | 屏幕与外部事件 | M6 剩余部分 |

**建议从 6a 开始**：改动面最小（只替换播放侧），收益最直观，而且不碰已经验证过的调度与决策链路。
