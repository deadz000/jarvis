# 面向实时交互的主从多 Agent 任务调度系统
## 开发实施计划 v0.1

> **文档状态：** 第一版实施计划，需随着 PoC 结果迭代。  
> **目标：** 把需求工作基线转成可执行的开发阶段、任务清单、交付物与阶段出口条件。  
> **当前进度：** 需求已形成工作基线；本计划制定时尚未完成新的 Pi SDK PoC。  
> **基本策略：** 先验证 Agent Runtime，再做确定性 Scheduler，随后接入 Master、交付层和多模态输入；不等待所有细节需求冻结后才开发。

---

## 1. 实施原则

1. **先做技术验证，不直接大规模编码。** 用最小程序确认 Pi SDK 的 Session、事件、工具调用、取消和持久化语义。
2. **先建可测试的 Scheduler，再接真实模型。** 任务状态、并发与取消必须能在没有 LLM 的情况下通过自动化测试。
3. **以完整目标为调度单位。** 同一目标的多步推理和工具调用默认由一个 Worker Agent Loop 完成；真正独立的目标才启动多个 Worker。
4. **实时通道优先级独立。** ASR 音频接收、VAD/停播控制和高频输入事件不能同步等待 Master。
5. **状态要有唯一写入口。** Master 输出声明式意图；Scheduler 验证后变更任务状态。
6. **先模块化单体。** 以明确模块和接口分层，不为了“架构完整”提前上微服务、Redis、Temporal 或通用 DAG。
7. **每阶段有退出条件。** 未验证的能力不能因为接口存在就标记完成。
8. **指标先采集后定阈值。** 先构造可复现测试并测基线，再冻结 p50/p95 或成功率要求。

## 2. 推荐的第一版技术骨架

### 2.1 已定与暂定

| 项目 | 当前建议 | 状态 |
|---|---|---|
| 语言 | TypeScript | 由 Pi TypeScript SDK 方向决定 |
| Agent Runtime | Pi TypeScript SDK | 已选择方向，包名与精确版本需 Phase 0 确认 |
| 服务端 | Node.js 常驻进程；HTTP/WebSocket 接口 | 建议；Web 框架可在骨架阶段比较后决定 |
| Scheduler | 自研、确定性状态机 | 核心自研模块 |
| Worker | 每个 Worker 独立 Agent Session | 设计原则已确认；实际并发/取消语义待 PoC |
| 输入 | 文本聊天、外部事件、屏幕事件、语音/ASR | 首版端到端目标，按阶段接入 |
| UI | 最小任务面板 | 建议；先显示任务状态、结果摘要和待交付状态 |
| 持久化 | PoC 先用内存；之后再选 SQLite/PostgreSQL 等 | 待决策，先避免存储选型阻塞 Agent 验证 |
| 语音 | 定义 ASR/TTS port，再决定复用旧管线或重新选型 | 待决策 |
| 测试 | 单元测试 + 集成测试 + 场景测试 | 必须从早期加入 |

### 2.2 Pi SDK 版本与包名核对（Phase 0 必做）

本计划暂以当前查阅到的 Pi SDK 文档为技术预研依据：<https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md>，文档中的包名为 `@earendil-works/pi-coding-agent`。建立项目时，必须确认最终使用的仓库、发布包、版本、许可证、运行时要求和 API。不要把这个仓库的代码示例与其他同名 Pi 项目或 fork 的包名混用。

Pi 文档目前描述的关键能力包括：创建 Agent Session、发起 prompt、订阅 AgentSession 事件、steer/follow-up、abort、会话管理。PoC 必须验证本项目实际需要的语义，特别是“abort 是否能停止自定义长任务工具”和“取消确认何时产生”。参考：<https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md>。

## 3. 里程碑总览

| 阶段 | 主要目标 | 关键交付物 | 通过标准 |
|---|---|---|---|
| M0 项目初始化与 SDK 核验 | 固定实际 SDK 来源/版本，建立最小 TS 工程 | 仓库骨架、依赖锁定、SDK 核验记录 | 能在目标开发环境创建 Session 并调用模型 |
| M1 单 Agent Runtime PoC | 验证工具循环、流式事件、会话与资源清理 | 最小 AgentSession 示例、测试记录 | 工具调用闭环与事件订阅正常，资源能清理 |
| M2 Worker Runtime Adapter | 将 Pi Session 包装成独立 Worker 执行单元 | Worker Adapter、任务事件模型 | 两个 Session 隔离并行；能收集运行事件 |
| M3 确定性 Scheduler | 在不依赖 LLM 的情况下实现 Task 生命周期 | Task 模型、状态机、并发控制、取消逻辑 | 单测覆盖关键状态转换、取消竞态与迟到事件 |
| M4 Master Decision Plane | Master 输出结构化建议，Scheduler 逐动作校验 | 候选 Schema、解析器、Validator/Compiler | 无效/过期动作不能破坏当前状态；合法动作可独立保留 |
| M5 Result & Delivery | 结果持久化接口、通知策略、音频仲裁抽象和最小面板 | Result Store、Delivery Policy、Audio Manager 接口、UI | 任务面板立即更新；普通结果不会无故抢播 |
| M6 混合输入端到端 | 接入聊天、外部事件、屏幕和语音/ASR/TTS | 输入适配器、统一事件层、端到端演示 | 四类输入可进入同一调度链路，实时链路不被模型阻塞 |
| M7 持久化、记忆与恢复 | 持久化任务/结果/决策；确定跨会话记忆与重启策略 | Storage Adapter、记忆策略、恢复流程 | 可查询历史结果；重启后状态符合选定恢复规则 |
| M8 系统评测与收敛 | 自动化场景测试、性能基线、失败注入与文档更新 | 评测报告、指标面板、发布候选版 | 核心场景可重复运行，指标可复算，未完成项有清单 |

**依赖关系：** M0 → M1 → M2/M3（可交替推进）→ M4 → M5；M6 可在 M3/M4 后以文本/模拟事件先接入，真实语音与屏幕逐步补齐；M7/M8 随端到端闭环推进。不要把整个项目等到 M8 才第一次演示。

## 4. 各阶段任务细则

### M0：项目初始化与 SDK 核验

**任务清单**

- [ ] 建立 Git 仓库、README、`.env.example`、配置加载和日志入口。
- [ ] 选择并记录 Pi SDK 的确切仓库、包名、版本/commit、许可证与兼容运行时。
- [ ] 固定依赖版本和 lockfile；区分模型 API 配置、凭据与业务配置。
- [ ] 验证目标开发环境（Windows 原生/WSL/Linux 待确认）能安装依赖并运行最小示例。
- [ ] 记录模型供应商、工具权限与环境变量，不提交 API Key。
- [ ] 创建架构决策记录 ADR-001：为什么选此 Pi SDK 包及其已知限制。

**交付物**

- 工程初始化提交。
- `docs/adr/001-pi-sdk.md`。
- 一条可运行的最小模型请求或 SDK session 示例。

**退出条件**

- SDK 来源和包名唯一且清楚。
- 新环境按 README 可以安装、配置和运行。
- API 凭据通过配置注入，不进入源码和日志。

### M1：单 Agent Runtime PoC

**任务清单**

- [ ] 创建 Agent Session，发起普通 prompt 并获得完成结果。
- [ ] 注册事件订阅，记录 text delta、工具调用、工具结果、错误和轮次结束等有用事件。
- [ ] 注册一个无副作用的自定义工具，验证模型调用工具、接收结果、继续运行并结束。
- [ ] 对照 SDK 文档验证 `steer`、`followUp`、`abort` 的语义和返回行为。
- [ ] 验证 Session disposal、重复请求、异常请求与超时后的清理。
- [ ] 验证 in-memory 与持久化 Session 的基本差异；暂不把会话历史当成任务状态数据库。

**建议测试**

- 单轮文本回答。
- 模型调用自定义工具后继续推理。
- 运行期间追加输入。
- 运行期间 abort。
- 工具执行超过预定时间时收到取消信号（如 SDK 可提供；否则记录 adapter 需要自行处理）。

**退出条件**

- 能解释 SDK 的事件生命周期，不只依赖 `prompt()` resolve 作为唯一状态信号。
- 能清理 Session 和订阅，不发生重复 listener 泄漏。
- 明确 SDK abort 和自定义工具取消的边界。

### M2：Worker Runtime Adapter

**任务清单**

- [ ] 定义 `WorkerRuntime` 端口：创建、启动、订阅、取消、回收。
- [ ] 每个 Worker 对应独立的 Agent Session / 会话历史。
- [ ] 所有输出事件关联 `taskId`、`runGeneration`，并包含事件类型和时间戳。
- [ ] 为工具事件和最终结果设定边界；Worker 不可直接变更 Scheduler 状态。
- [ ] 定义 Worker 的错误、超时、取消请求及结束信号。

**退出条件**

- 两个 Worker 能在运行时间上实际重叠。
- 两个 Worker 的上下文、工具事件和结果正确隔离。
- 一个 Worker abort 不影响另一个 Worker。

### M3：确定性 Scheduler

**任务清单**

- [ ] 定义 Task 和 Execution（Task ID 与 run generation 分离）。
- [ ] 实现候选状态：`queued`、`running`、`cancel_requested`、`succeeded`、`failed`、`cancelled`，并对 PoC 后的调整留变更记录。
- [ ] 实现单一状态写入口、事件发布、状态转换校验。
- [ ] 实现最小并发上限和准入队列；数值先配置化，不直接硬编码旧项目值。
- [ ] 实现单任务取消，不影响无关任务。
- [ ] 实现取消与自然完成/失败竞态处理，以及旧 run generation 迟到事件过滤。
- [ ] 用 FakeWorker 完成确定性测试，不调用真实 LLM。
- [ ] 加入结构化日志与关键时间戳。

**必须覆盖的状态测试**

- queued → running → succeeded。
- queued → cancelled。
- running → cancel_requested → cancelled。
- cancel_requested 与 succeeded/failed 同时到达的竞态。
- 旧 generation 的进度/结果迟到。
- 两个任务并行，一个失败另一个成功。
- 并发超限后的准入行为。

**退出条件**

- 不使用 LLM 也能验证任务状态和并行控制正确。
- 所有非法转移可被检测，不静默破坏状态。
- 事件重复或迟到不会让任务回退到旧状态。

### M4：Master Decision Plane

**任务清单**

- [ ] 定义送给 Master 的有界上下文视图：最新用户输入、相关屏幕/事件摘要、必要的活动任务摘要、最近完成摘要。
- [ ] 设计首版候选 `MasterDecision` Schema。字段先围绕启动任务、取消任务、焦点建议和决策依据设计，不把内部 Runtime 对象暴露给模型。
- [ ] 将模型输出解析和业务校验分开；无效 JSON/schema 输出有安全降级路径。
- [ ] 加入 `decisionId` 与状态 revision/snapshot 关联；revision 如何分维需根据 PoC 决定，不提前硬编码复杂三维版本体系。
- [ ] 按动作逐条校验：某个取消目标失效不应必然丢掉计划内仍合法的独立启动动作。
- [ ] 设定 Master 超时降级：默认不执行无法确认的破坏性动作；具体超时值基于模型实测配置。
- [ ] 防止重复 decision 重复启动 Task；为动作或命令设计幂等键/去重规则。

**退出条件**

- Master 只能提出意图，不能直接写 Task 状态。
- 过期决策不能错误取消已经完成/重启的任务。
- Schema 错误、超时和部分动作失效均有可测试的处理方式。

### M5：结果管理、交付策略与任务面板

**任务清单**

- [ ] 定义 Result 记录：taskId/runGeneration、摘要、完整内容/产物引用、创建时间、来源和状态。
- [ ] 使 Task 成功与 Delivery 状态独立。
- [ ] 实现结果就绪后面板更新；初期用最小任务面板或开发控制台即可。
- [ ] 定义候选 Delivery 状态和可重试交付事件；不因 TTS 错误把 Task 改成 failed。
- [ ] 实现默认策略：普通结果不抢占当前播报；更高优先级的待交付结果在当前语句结束后优先；紧急抢占暂不启用，除非先定义紧急条件。
- [ ] 定义 `AudioManager` 端口，并模拟播放队列、Hard Stop、播放 token/generation 与旧音频拒绝。
- [ ] 任务完成事件可能重复到达时，保证结果记录和通知行为具有幂等性。

**退出条件**

- 任务面板与结果记录在任务完成后无需等待语音播放。
- 多个结果就绪时不丢失、不串任务。
- 普通结果不会抢占正在播报的内容；旧播放代次不复活。

### M6：混合输入端到端接入

**实施顺序建议**

1. 聊天文本输入：验证完整 Master → Scheduler → Workers → Results 链路。
2. 外部事件适配器：用真实或 mock 事件统一接入 Event Ingress。
3. 屏幕上下文：先实现显式启停、事件/有限频率采集、变化过滤、按需上下文引用；原始帧留存策略先保守。
4. 语音：接入 ASR partial/final、VAD/用户开口事件、TTS 输出。先定义 port，随后决定复用 CclawCore 的既有 ASR/TTS 或重选供应商。
5. 将高频音频接收、语音活动和必要停播控制放在不受 Master 阻塞的独立任务/通道中。
6. 对长时间操作定义可取消接口；无法取消的工具明确报告而不伪装成功取消。

**退出条件**

- 文本、外部事件、屏幕事件、语音转写均能进入统一事件模型。
- 输入事件可以在 Master 推理期间继续被接收和记录。
- 屏幕采集有显式控制和过滤；语音停播不直接取消任务。
- 从输入到任务执行、结果保存与面板展示能端到端演示。

### M7：持久化、跨会话记忆与故障恢复

**任务清单**

- [ ] 根据单机部署/并发需要选择存储（SQLite/PostgreSQL 等）；先不在 PoC 阶段引入额外数据库基础设施。
- [ ] 持久化任务、执行代次、结果、必要事件和决策轨迹。
- [ ] 定义服务重启时 `running` / `cancel_requested` 状态的保守处理流程：不得假设进程重启前的工具已停止，也不得盲目重跑副作用工具。
- [ ] 支持查询历史任务结果。
- [ ] 按记忆策略逐步加入用户偏好、长期目标和任务摘要；区分任务记录与语义记忆。
- [ ] 定义数据保留、更新和删除机制。
- [ ] 注入服务重启、ASR/TTS 断连、Worker 错误和重复/迟到事件进行测试。

**退出条件**

- 历史任务和结果可以正确查询。
- 重启后的未知执行状态能被明确标记和核对。
- 恢复不会在未核对的情况下自动重复执行可能有副作用的操作。

### M8：评测与交付

**任务清单**

- [ ] 对核心场景建立可重复脚本和固定测试输入。
- [ ] 实现可控延迟的 FakeWorker、FakeMaster、模拟 ASR/TTS 和事件回放。
- [ ] 输出调度延迟、停播延迟、取消成功率、任务完成率、交付延迟、误打断率与恢复正确率。
- [ ] 报告均值、P50、P95 和样本数；区分模型调用耗时与 Scheduler 自身耗时。
- [ ] 做故障注入与并发测试。
- [ ] 根据结果确定正式验收阈值，更新需求文档和 ADR。

**退出条件**

- SC-01 至 SC-05 可重复演示；记忆/恢复能力按最后冻结的 MVP 边界验收。
- 指标能从结构化事件重算，而不依赖人工读日志。
- 所有未完成需求、已知限制和未验证能力在文档中透明列出。

## 6. 测试与可观测性要求

### 6.1 必备关联字段（最终 Schema 待定）

- `eventId`：来源事件。
- `decisionId`：Master 决策请求/结果。
- `taskId`：独立目标。
- `runGeneration`：任务执行代次。
- `sessionId`：Pi Agent Session。
- `timestamp`：事件时间。
- `actionId` / 幂等键：一次调度动作（若使用）。

### 6.2 单元测试优先级

1. Task 状态转换和非法转移。
2. cancel 与 finish 竞态。
3. 旧 runGeneration 迟到事件。
4. MasterDecision Schema 与按动作验证。
5. 重复决策不重复创建任务。
6. 并发准入队列。
7. Result 就绪与 Delivery 独立。
8. Audio playback token 旧代次过滤。
9. 事件去重、节流和有界队列。

### 6.3 不依赖真实模型的可测试性

Scheduler 的大多数正确性测试必须能够通过 FakeMaster/FakeWorker 运行，确保测试稳定、低成本、可复现。真实模型只用于验证意图理解和端到端体验；不要用不稳定的自然语言输出测试所有状态机边界。

## 7. 风险与规避

| 风险 | 规避方式 |
|---|---|
| Pi API 行为与预期不符 | M0/M1 先写小型验证；Pi API 隔离在 adapter 后 |
| 调度逻辑过度依赖 LLM | 声明式计划 + Schema + 确定性 Scheduler + 按动作校验 |
| 需求过大，端到端目标拖延 | 先用 mock 把核心闭环跑通，再按 adapter 逐步接入真实输入 |
| 实时输入被模型调用阻塞 | 独立接收任务、事件队列和播放控制；Master 只消费快照/摘要 |
| 误取消或迟到事件污染 | task ID + run generation、动作前置条件验证、幂等处理 |
| Worker 互相污染上下文 | 每个 Task 创建独立 Session，显式提供最小必要上下文 |
| 取消只停模型、不停工具 | 自定义工具需支持 abort signal/取消检查；记录不可取消操作 |
| 任务完成与交付状态混淆 | 独立 Task/Result/Delivery/Audio 状态模型 |
| 屏幕隐私和推理成本失控 | 显式启停、变化过滤、节流、按需注入、保守保留策略 |
| 过早引入基础设施 | MVP 模块化单体，PoC 内存存储；测量后再决定数据库/队列/工作流引擎 |

## 8. 首个可演示增量（Milestone Alpha）

**目标：** 不接真实语音、不接屏幕、不建设长期记忆，也能证明核心架构可行。

演示流程：

1. 用户通过简易聊天输入：“总结最近三次 Git 提交，同时查询天气”（两个可以独立调度的任务；可先用 mock 工具）。
2. Master 返回结构化的两个任务建议。
3. Scheduler 创建两个独立 Task 和 Worker Session。
4. 两个 Worker 并行执行，并回传事件与结果。
5. 用户输入“取消天气任务”；Scheduler 只向目标 Worker 发起取消，不影响 Git Worker。
6. Git Worker 完成，结果记录与任务面板立即更新。
7. 用模拟 Audio Manager 验证：若当前正在播报另一结果，普通通知排队；停播后旧播放代次不会复活。
8. 日志能够重建事件、决策、任务状态与交付时间线。

**Alpha 退出条件：** 上述流程可重复运行；核心状态机测试通过；能展示并行、单任务取消、上下文隔离、结果状态独立和旧代次过滤。达到后再接入真实 ASR/TTS 与屏幕采集。

## 9. 首版不做清单

为了避免项目范围失控，首版暂不承诺：

- 通用 DAG / 任意依赖图工作流引擎。
- 复杂的 Task 挂起/恢复状态机（除非测试场景证明必须）。
- 多服务分布式部署、分布式锁和分布式任务队列。
- 对每一帧音频/屏幕变化都调用 Master LLM。
- 对所有工具执行无限制自主权限。
- 未经验证的自动故障恢复与副作用操作自动重试。
- 以历史 CclawCore 的参数直接定义新系统阈值。

## 12. 定义完成（Definition of Done）

任一功能只有满足以下条件才算完成：

- 有明确的需求 ID 或 ADR 关联。
- 有单元或集成测试覆盖正常路径和至少一个关键失败/竞态路径。
- 状态变化和失败原因有结构化日志。
- 不在没有明确记录的情况下改变已确认的行为原则。
- 运行步骤与配置更新到 README/文档。
- 没有把“已发出取消请求”误报为“已停止”，没有把“结果已生成”误报为“已交付”。
- 对仍未验证的边界标记为 limitation，而不声称已完成。
