# 演示脚本（Milestone Alpha）

> 对应《开发实施计划 v0.1》§8「首个可演示增量」。
> 目标：**不接真实语音、不接屏幕、不建长期记忆**，也能证明核心架构可行。
> 全部能力已于 2026-10-10 实测通过。

---

## 启动

```powershell
npm install          # 首次
npm run demo         # 启动演示面板（默认 http://127.0.0.1:7717）
```

浏览器打开打印出的地址。端口可用环境变量覆盖：`$env:JARVIS_DEMO_PORT=8800`。

面板分四块：左侧**对话输入**、中间**任务面板**、右侧**交付队列 + 音频仲裁**、底部**事件时间线**。
顶部实时显示模型、两维版本号（`e` = eventSeq，`c` = controlRevision）与连接状态。

## 场景 1：两个独立目标并行（Alpha 步骤 1–4）

点「查天气 + 总结 Git 提交」，或自己输入：

> 查一下今天的天气，同时总结最近三次 Git 提交

**应该看到**：Master 返回**两个** `start_task`；任务面板出现 `task-1`、`task-2`，
两者同时处于 `running`（`gen 1`），时间线里两条任务的进度事件交替出现。

**证明**：任务拆分以独立目标为单位；两个 Worker 各用独立 Session 真实并行。

---

## 场景 2：一个目标内的多步骤（不拆分）

> 分析项目最近的 Git 提交，并根据分析结果总结项目风险

**应该看到**：只创建**一个**任务，它在自己的 Agent Loop 内多轮调用工具，最终给出一个结果。

**证明**：拆分单位是目标，不是步骤；不会把中间推理误报成独立任务完成。

---

## 场景 3：取消隔离（走 Master 推断）

在场景 1 的任务还在跑时，输入：

> 天气不用查了，继续分析 Git 提交，把焦点放在 Git 那个任务上

**应该看到**：决策里只有**一个** `cancel_task`（指向天气任务）和 `set_focus`；
天气任务变为 `cancel_requested` → `cancelled`，**Git 任务继续跑完**。

**证明**：停播 ≠ 取消；取消只影响目标任务；Master 只能建议，落地经 Scheduler 校验。

---

## 场景 4：结果交付不抢占播报（Alpha 步骤 6–7）

让两个任务几乎同时完成。**应该看到**右边「交付队列」里：

- 第一个结果状态 `播报中`，第二个 `排队中`；
- 时间线出现 `delivery_deferred`：*「当前正在播报 task-x，普通结果不抢占」*；
- 第一条播完后，第二条才开始交付。

**证明**：面板更新不等播报；普通结果不抢占；任务完成状态与交付状态相互独立。

---

## 场景 5：停播后旧代次不复活（Alpha 步骤 7 的关键不变量）

播报进行中，点右侧「**模拟用户开口 → 停播**」，然后点「**重放旧代次分片**」。

**应该看到**：

- 音频面板「当前播放代次」前进（例如 `#1` → `#2`）；
- 「已作废代次」记下被停播的那一代；
- 点重放后「**分片：已拒绝**」计数 +1，时间线出现
  `audio_playback_chunk_rejected`：*「分片被拒绝（token #1 已失效）」*。

**证明**：播放是受控单例资源；「是谁」（taskId）与「哪一次」（token）分离；
旧代次残留音频被拒绝而不是静默丢弃。

## 直接调 API（不经过界面）

```powershell
# 当前快照
Invoke-RestMethod http://127.0.0.1:7717/api/state

# 发一句话（注意：PowerShell 需显式 UTF-8，否则中文会变成 ???）
$json  = @{ text = '查一下今天的天气，同时总结最近三次 Git 提交' } | ConvertTo-Json -Compress
$bytes = [System.Text.Encoding]::UTF8.GetBytes($json)
Invoke-RestMethod http://127.0.0.1:7717/api/chat -Method Post -Body $bytes -ContentType 'application/json; charset=utf-8'

POST /api/cancel            { "taskId": "task-1" }
POST /api/audio/stop        {}
POST /api/audio/replay-stale {}
GET  /api/events            # SSE 实时推送
```

## 实测基线（2026-10-10，`cf-fan/deepseek-flash`）

| 项 | 观测值 |
|---|---|
| Master 决策耗时 | 2.5–2.8s（超时上限 30s） |
| 两个独立任务拆分 | ✅ 一次决策产出 2 个 `start_task` |
| 两个真实 Session 并行重叠 | 1818ms |
| 取消请求下发延迟 | 3ms（执行层确认由 `worker_cancelled` 给出） |
| 停播后台次推进 | `#1` → `#2`，旧代次分片 `rejected = 1` |
| 单元测试 | 106 项通过（不调用 LLM） |

## 已知限制（**不要**当作已实现）

| 限制 | 说明 |
|---|---|
| **未接真实 ASR / TTS** | 音频为模拟仲裁，只为验证播放代次语义；语音选型是 SRS §11.6 待决策项（属 M6） |
| **未接屏幕 / 外部事件** | 输入只有聊天文本（M6） |
| **Worker 有内建工具且未沙箱** | 演示里的 Worker 可用 `read`/`bash`/`edit`/`write`，工作目录就是本仓库；工具白名单与沙箱属 SRS §11.8 待决策项 |
| **结果不持久化** | 全部在内存，重启即丢（M7） |
| **无优先级抢占与饥饿防护** | 准入为 FIFO；`priority` 只影响**交付顺序**，不影响调度顺序（M8 再定） |
| **无取消超时看门狗** | 执行层既不确认停止也不报终态时，任务会停在 `cancel_requested`（M7） |
| **紧急抢占未启用** | 紧急条件未定义（SRS §11.5，属 M5） |
