# 交付策略与优先级：LLM 决策与确定性仲裁的分工（v0.1）

> **触发**：项目负责人提出「结果交付和优先级这些我也想交给 LLM 决策」。
> **结论**：方向同意，但必须把**语义决策**与**动作时机**分开 —— 前者交给 LLM，后者保持确定性。
> **待确认**：抢占许可条件（见 §5）。确认后即可实现。

---

## 1. 为什么不能把"何时切换音频"也交给 LLM

这不是架构洁癖，是我们这个项目**自己实测出来的数字**：

| 事实 | 数值 | 影响 |
|---|---|---|
| Master 决策耗时（真实模型） | **2.5–2.8s** | 每句话边界都等 LLM → 打断延迟 3 秒起，这正是旧项目"打断延迟十几秒"的成因 |
| 播放是**受控单例资源** | 单例 + token | 把切换时机交给概率模型，会出现「同一结果播两次」「旧音频复活」（旧项目坑 3） |
| 停播是**实时**需求 | 目标 < 100ms | LLM 在 2.5s 尺度上，比目标慢 25 倍 |
| 旧项目的教训 | 坑 12 | 「用户一开口就 cancel」→ 白烧整次 Agent 调用；后来演进为「独立 LLM 分类器 → Master 统一语义调度」**但仍由确定性执行器落地** |

**所以：LLM 判断"这件事重不重要、要不要打断用户"，确定性仲裁器执行"在哪一刻切换音频"。**

## 2. 分工表

| 决策 | 谁定 | 理由 |
|---|---|---|
| 结果的**重要性/紧急度**（low→urgent） | **LLM** | 纯语义判断，确定性规则写不出来 |
| 是否需要**打断用户**（interrupt 意图） | **LLM** | 同上；这正是旧项目 v2 演进的产物 |
| 是否与他人结果**合并成一句** | **LLM** | 需要理解语义相关性 |
| 实际**何时切换音频**（串行化、句子/分片边界） | **确定性仲裁器** | 实时 + 单例资源 + 需要 token 代次保证 |
| **是否允许抢占**（许可条件） | **你（产品规则）** | 例如「只有 urgent 才可抢占」；见 §5 |
| 抢占的**粒度**（立即切断 vs 分片边界） | 确定性仲裁器（按你给的规则） | 立即切断会造成句子截断、体验差 |

## 3. LLM 在哪几个时机给出交付判断（延迟/成本对比）

| 方案 | 时机 | 额外延迟 | 额外成本 | 评价 |
|---|---|---|---|---|
| **A. Worker 结果自评** | 产出结果的那次运行内，顺带输出 | **0** | **0** | ⚠️ **只能给"结果自身的事实"**，给不出重要性 —— 见 §3.1 |
| **B. 独立分类器（带参照物）** | 结果就绪后单独调一次 | 一次调用 | 一次调用 | ✅ 唯一能产出**重要性**的方案：它能看到用户最新输入、焦点、待交付队列 |
| **C. Master 统一调度** | 下一次自然决策时重排队列 | 0（复用） | 0 | 参照物最全，但"下一次决策"可能很晚，结果会一直压着 |

#### 3.1 为什么 Worker 自评给不出「重要性」

重要性是**相对的**，需要参照物；Worker 只看得见自己的目标。因此把判断拆成两层：

| 自评**能给**（结果自身属性，自足可判） | 自评**给不了**（相对重要性，需要参照物） |
|---|---|
| 目标是否达成 / 部分完成 | 用户此刻还要不要这个结果 |
| 是否**需要用户决策**才能继续 | 用户是否正在听另一条播报 |
| 是否含**阻塞 / 失败** | 相对其他待交付结果谁更急 |
| 是否发现**额外风险** | 用户是刚问的（在等）还是很久以前问的（已转移） |

**结论**：Worker 只报事实（`needsUserDecision` / `hasBlocker` / `isBadNews` / `isPartial`），
**重要性由带参照物的分类器判定**，参照物来自 `WorldModel` 的有界视图。

**推荐组合**：
1. Worker 自评只产出上述事实（零成本）；
2. 确定性规则把绝大多数结果处置为「排队、不抢占」（零成本）；
3. **仅当事实命中「可能需要打断用户」**（如 `needsUserDecision` / `hasBlocker`）时，
   才调用一次带参照物的分类器，产出 `importance` 与 `interruptUser`；
4. 由确定性仲裁器执行（已确认规则：仅 `urgent` 可抢占，且只在分片边界停）。

这样普通结果的额外调用次数为 **0**，而真正高风险（可能打断用户）的判断拿到了完整参照物。

## 4. 我准备怎么实现（不改动已验证的部分）

1. **扩展决策契约**（ADR-003 的 Schema）新增交付相关动作/字段：
   ```ts
   { type: "set_delivery_policy",
     taskId: "task-1",
     importance: "low" | "normal" | "high" | "urgent",
     delivery: "immediate" | "queue" | "defer" | "panel_only",
     mergeWith: "task-2" | null,
     interruptUser: boolean,
     reason: "..." }
   ```
   仍然遵守 ADR-003 的规则：逐动作校验、幂等、超时降级为空计划。
2. **Worker 结果自评**：`WorkerEvent` 的 `worker_succeeded` 增加可选 `importance` / `interruptUser`（由 Worker 的提示词要求输出）。
3. **确定性仲裁器**（现有 `DeliveryQueue` + `SimulatedAudioManager` 的演进）：
   - 保留**不抢占为默认**：播放中的结果永远排队，等当前语句结束；
   - 按你确认的**许可条件**决定是否允许抢占；
   - 抢占时**先在分片边界停**（不截断句子中段），再推进代次 token；
   - 旧代次分片一律拒绝并记账（这条已实现且被测过）。
4. **可测试**：仲裁器已有手工定时器注入，新增的抢占规则同样可确定性单测，不需要真实 TTS。

## 5. 已确认的产品规则

### 5.1 抢占许可条件 ✅ 已确认

**仅 `urgent` 可抢占，且只在该结果被判为 urgent 时才触发；抢占在分片边界停，不截断句子中段。**

已实现于 `src/application/delivery/`：
- `SimulatedAudioManager.requestStopAtBoundary(reason)`：请求在下一个分片边界停止（而非立即切断）；
- `DeliveryQueue`：当 `urgent` 结果入队且当前正在播非 urgent 内容时，请求边界停止；
  边界到达后停播并优先交付 urgent 结果；
- 已在播 urgent 时不再触发抢占；普通结果永不请求抢占。

### 5.2 重要性由谁产出 ✅ 已修正

原建议（Worker 自评重要性）**不成立** —— 自评没有参照物，给不出相对重要性。
修正为：**Worker 只报自足事实，重要性由带参照物的分类器判定**（见 §3.1）。
分类器的接入属下一步实现；当前已落地的是确定性处置与抢占执行。
